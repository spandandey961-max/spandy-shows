# Spandy Shows supported programs

See your code, step by step.

## Python

Verified on CPython 3.12.14. Single-file programs: standard-library imports, built-in functions, assignment, loops, user functions/arguments/returns, recursion, generators and generator expressions, async functions/await, lists, tuples, dictionaries, sets, user classes with dictionaries or slots, nested/shared/cyclic objects, exceptions and standard input. Code executes under CPython; there is no simulated evaluator.

Both Run code and Visualize use normal Python imports and builtins. The visualizer records only the submitted source, including callbacks invoked by libraries; it does not step through library implementation files. Generator yields and async suspension/resumption preserve the frame identity and are labeled separately from final returns. Python tracing covers the main execution thread, not all threads created by a library. Library/native objects whose storage cannot be inspected are labeled unavailable; user representations/getters are never invoked for inspection. Collections and variable scopes remain bounded and marked when truncated. Third-party Python packages are available only if installed in the worker environment. A missing dependency produces the real ModuleNotFoundError. GUI windows, multi-file projects and custom runtime arguments are outside this web editor. Trusted-local execution is not a security sandbox; do not expose it to untrusted input.

## Java

Verified on Temurin OpenJDK 21.0.12.1. One source file with a static main(String[] args) entry point. The service derives the filename from the top-level public class (for example UtilityProgram.java) and launches the class containing main. Package declarations are supported. Primitive locals, conditionals/loops, methods/recursion, arrays, strings, user classes declared in the same source file (including helper classes), static fields, exceptions and standard input. Compiler debug data and JVM/JDI observations determine states. Standard JDK packages such as java.util, java.math and java.time can be imported and called in both modes; their implementation steps/internals are hidden.

Multiple source files, external JAR/classpath configuration and GUI are outside this editor. Run code uses the actual JVM without visualization scope checks. Visualize remains single-threaded and rejects detected thread creation, native methods and process control; ordinary Runtime library queries are allowed. Comments and strings are excluded from those checks. Strings are shown as values rather than heap-identity diagrams. Local names become visible only when the compiler marks their initialized scope; the viewer does not fabricate absent locals. Debugger return values are shown when JDI supports them.

## C

Verified on WinLibs GCC 16.2.0 / GDB 18.1. C17, one main.c, debug symbols and -O0. Standard headers/functions such as stdio.h, stdlib.h, string.h, ctype.h and math.h are available, with libm linked for math calls. Primitive observations, loops/conditionals, functions/recursion, 1D/2D/3D arrays, runtime-sized arrays, structs, static/global symbols, standard input/output, observed stack pointers and null pointers. malloc/free execute normally, but allocated heap contents and lifetime are not reconstructed. Typed storage and bounded array elements are observed before pointer linking; rows and their containing array keep distinct identities even when addresses overlap. Array bounds come from debugger type information.

Initialization status for stack values remains **unknown** without additional instrumentation; observed bytes can be uninitialized. Declarations not yet executed are shown as ?. A VLA is not read until its declaration has executed, avoiding uninitialized debugger bounds. The C workspace describes the remaining initialization limitation in Help and observation details. Pointer values alone do not prove validity. Pointers matching displayed symbols, struct fields, array rows or individual elements receive arrows to that exact destination; unknown or cropped targets remain addresses with no dereference. Pointer arithmetic executes normally and links to displayed destinations. Dynamic allocation/free lifetime, full memory safety and out-of-bounds validity are not reconstructed. Unions, optimized code, multi-file code, threads/processes/networking and inline assembly are outside supported visualization. Run code uses GCC without those visualization scope checks. External headers/libraries and platform-specific APIs require a compatible installed toolchain and build configuration; they are not automatically downloaded. C return-value inspection is unavailable; returned calls are inferred from the real debugger stack change and labeled with caller timing.

Direct C stdin calls (`scanf`, `fscanf`, `vscanf`, `vfscanf`, `getchar`, `fgetc`, `getc`, `fgets`) use a separate helper calling the actual libc reader. Interactive stdin is a blocking named pipe on Windows or FIFO on POSIX. A read can resume across multiple responses without restarting the program or repeating a partially completed conversion. Buffered newline/token behavior is preserved. Mismatched types and failed conversions stop with `input_invalid` or `input_required`, preserving output and preventing user code from using unread destinations. Simple direct destinations are hidden as **awaiting input** until a successful read is observed; this is a conservative display policy, not general C initialization analysis. The guard intentionally stops failed reads even when user code checks scanf's return value. EOF-driven programs and indirect/custom readers remain outside this workflow.

## All languages

Program input appears below Output at an actual blocked read. Enter submits one response, including an explicit empty line when appropriate. Python and Java use blocking input adapters; C uses the real libc reader on a pipe. The same process continues; previously recorded steps never re-execute. Type hints come from the current input statement, and the runtime validates conversions. Java charAt(0) retains its normal first-character semantics. Invalid conversions produce runtime diagnostics. Correct the input by starting a new run. Waiting pauses the active execution budget, with a three-minute idle limit.

Programs accept up to 10,000 source lines and 1 MiB of UTF-8 source, including saved/shared programs. Source, input and debugger locations above line 1,000 are retained. Source length and recorded execution length are separate: Visualize still has a 20,000-snapshot, 64 MiB trace and 300-second active preparation limit. Run code has a 60-second active budget; time awaiting input is excluded.

No accounts are required. Run code executes without the 20,000-snapshot limit and shows final output. Visualize produces a bounded trace; stepping backward/forward replays snapshots without side effects. Editing source or language stops execution/playback and invalidates the displayed trace. Submitting a runtime response continues the current execution. Step explanations compare actual recorded values; highlighted before-line snapshots show what executes next. Phone/tablet layouts show code, input and output together in a stacked page. Objects & memory is initially collapsed and only offered when relevant actual records exist. Java's unused empty startup argument array is omitted from the display, without changing raw API traces; explicitly used arguments and user arrays remain visible. Python Run code may inspect final objects; Java and C object inspection requires Visualize.

Keyboard: Enter in Program input continues the waiting execution, Ctrl/Command + Enter runs from the editor, Ctrl/Command + Shift + Enter visualizes. Arrows step, Space plays/pauses, Home/End and Ctrl/Command + Left/Right jump to first/last; replay shortcuts leave editor typing and form fields alone. Dialogs use native focus trapping, buttons have labels/focus rings and reduced-motion preferences disable animation. Copy code copies the entire source. Themes cover all page surfaces and the editor. Output keeps its whitespace and expands vertically; banners scale down to 8px, with horizontal scrolling only for unusually wide content. The diagram is educational, not an exact physical memory layout.

Array presentation uses indexed cells for 1D arrays, rows and columns for 2D arrays, and labelled slices for 3D arrays, including nested Java arrays and Python lists. Shared rows and cycles retain their reference identities. C observes up to 512 cells per snapshot, in addition to the existing depth/object/collection bounds; execution uses the complete arrays. The bundled GDB Python observer reads only the bounded visible storage, without creating an unbounded var-object tree.
